# Mobile WebGPU recovery

## Physical-device retest: still unresolved

The user retested live version 6 on physical Qualcomm / Adreno-8xx with compatibility selected and the GEO / FUSE C220 scene. It still received `GPU device lost (unknown) during Compiling trace: A valid external Instance reference no longer exists.` Compact mode and the lifecycle/error-reporting improvements do not fix this phone's startup failure. A passing desktop test cannot establish a phone fix.

A second physical-phone report reproduced the failure in the isolated **current trace** comparison in full Chrome 154, with `embedded=false`, a visible document and no recorded lifecycle event. The device was created, the exact 24,033-byte trace source had SHA-256 `563e314d2f974482c1b24c890067316eab892b7adeb8806ad688b15527a60b3f`, and its one shader-info request completed with no validation messages. The device then reported `unknown` loss and a `GPUPipelineError` during compute-entrypoint compilation, before check closure and without timeout. No scene/frame buffers or GPU bytes were allocated by this case. This reproduces pipeline-creation failure without scene memory and after frontend validation; it does not establish a shader-size or browser/driver root cause. A reduced Android user-agent string does not establish the actual Android version. A tiny-control pass has not yet been established on this phone.

The physical adapter advertised 2 GiB maximum buffers, 16 storage bindings, 1,024 compute invocations and 32 KiB workgroup storage. The requested device used no optional features, 512 MiB maximum buffers/storage bindings and 32 KiB workgroup storage. Its resulting limits included eight storage bindings and 256 compute invocations. Requested capacities are limits, not preallocated memory. The default-limit comparison is retained to test this request separately.

The exact message can arise when Dawn cancels pending callbacks during API-channel teardown. [Dawn's wire client](https://raw.githubusercontent.com/google/dawn/main/src/dawn/wire/client/Client.cpp) destroys instance event managers on disconnect, and [Blink maps CallbackCancelled to JavaScript unknown](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/webgpu/gpu_device_lost_info.cc). This does not identify the Android browser/driver cause or establish JavaScript garbage collection as the cause. The displayed stage is the outstanding operation when failure became visible.

Source ordering shows no scene worker, scene GPU buffers, frame buffers or first frame submission before trace compilation. Only a 16-byte diagnostic uniform buffer and a configured canvas are present. Four shader modules are prepared before compute pipelines. The current trace is 24,033 UTF-8 bytes with 34 functions, a 64-entry private BVH stack, two 16-entry medium stacks, and nested guide/branch/bounce loops. Private WGSL data size is not measured GPU memory or register usage.

[GPU startup comparison](../browser/gpu-compile-check.html) reports the diagnostic build, browser, adapter/device/requested limits, module-validation completion, outstanding operation, allocation ordering, exact shader hash, and error/loss data. Controls include a tiny shader; an unused entrypoint in full trace source; current trace with renderer/default limits; workgroup-only and medium-capacity-only variants; both together; and the original startup prefix. Run one selected case or one sequential comparison starting at the selected case. Each case gets a fresh device and closes it; the sequence stops on its first failure, loss, timeout or user stop. It does not continue requesting devices after a lost-device result. A single 40-second deadline covers each case's adapter/device requests, source preparation, shader-info requests and pipelines. A device delivered after timeout or cancellation is destroyed. Loss cancels a pending pipeline even if its callback never settles. The prefix records each module's creation, shader-info request count, completion and messages, and reuses the completed trace report instead of requesting it again.

Every stage is visible and checkpointed in browser-local storage, with session storage as a fallback. Reload restores the last complete or partial report; an unfinished check is not automatically rerun over its evidence. Storage denial does not prevent compilation or cleanup. Copy includes completed sequence cases and the pending/failing stage; Clear removes the local report. Reports and device logs are not uploaded. Scene/frame buffers are not loaded by the check.

The [compile isolation plan](ADRENO_COMPILE_PLAN.md) describes which physical control distinguishes each remaining hypothesis and how to bisect active compilation without changing renderer behavior.

The first NVIDIA comparison advanced through seven isolated compute controls, then stalled in the startup-prefix case before its aggregate harness preserved individual reports. A later run saved each result independently and completed in 51.9 seconds including resource cleanup. At the reported 960x540, six-bounce, one-optical-sample configuration, default and explicit compact rendering produced identical raw, temporal and final hashes after eight frames. The actual device-loss/retry and persisted-page-return checks passed, as did the tiny compute control. This proves preservation for that desktop configuration; it does not establish physical Adreno compatibility or cover every bounce setting.

The later startup-prefix check hit its own 40-second deadline after all four initial shader-info requests had completed, with no device-loss or page-error report. Its next operation redundantly requested trace shader information again. The check now retains and reuses the completed trace report; CPU tests execute the actual page controller with a fixture that rejects repeated requests and confirm cached validation errors remain visible. This final diagnostic-only correction has not been rerun on a GPU. The timeout is separate from the physical Adreno startup failure and is not evidence of its cause.

The explicitly selected `gpuCompatibility=compact` candidate retains the actual renderer and all supported scene/settings/transport behavior. It uses 4×4 trace workgroups and ten medium slots, matching the existing maximum ten-bounce UI. Traversal capacity, Fresnel split, water/glass absorption/IOR, stochastic paths, terminal emission and reconstruction are retained. The normal/default path is unchanged. Corrected and separate-signal transport experiments require their original capacities and reject this candidate explicitly. The physical version-6 retest confirmed that this comparison is not a fix on the reported Adreno phone.

The reported device was Qualcomm / Adreno-8xx, on proof-optics, interactive temporal reconstruction, 960×540, six bounces and one optical lighting sample. Its visible error was `A valid external Instance reference no longer exists.` The adapter label is assigned after `requestDevice` succeeds. The original host caught pipeline, submission and timing-readback failures in the same status field; those could replace the device-loss reason.

The exact browser text is not sufficient to infer a JavaScript lifetime defect or a shader defect. A [WebGPU maintainer response](https://github.com/gpuweb/gpuweb/discussions/4676) identifies it as Chromium-specific and requests a detailed reproduction. The original host also had a separate confirmed lifecycle defect: `pagehide` destroyed its device and controls with no `pageshow` recovery for a cached document.

The host now owns the GPU, adapter, context and device through the session; records compilation/load/render phase; preserves loss reason and the first failure; cancels pending compilation when leaving or losing the device; and reloads a cached document into a fresh session. A visible retry button preserves selected settings and requests a fresh device. Mobile or explicit recovery sessions serialize pipeline compilation and omit optional timestamp queries/readback. Desktop defaults and explicit `gpuTimings=1` keep GPU timing. Buffer creation checks actual device allocation and storage-binding limits before asking the GPU for an invalid resource.

The lifecycle changes do not alter shader, geometry, resolution, sample/bounce, denoiser, reconstruction or transport math. The 64 recorded renderer implementation digests remain unchanged. The separately selected compatibility candidate changes only trace workgroup shape and medium capacity. Mobile compilation sequencing reduces concurrent driver compilation work, and removing optional queries avoids that diagnostic driver path; neither is presented as proof of the Adreno root cause.

CPU tests cover feature/limit negotiation, exact compilation descriptors/order, bounded compilation concurrency, loss/error precedence, cancelled startup, intentional shutdown and buffer limits. The comparison-page tests execute its actual controller, including a device fixture that loses its device while a pipeline callback stays pending, sequential stop behavior, restored checkpoints, unavailable storage and late-device cleanup. Browser validation must distinguish actual desktop GPU execution with mobile layout from physical Adreno execution. Physical-device success remains unverified; current isolated trace failure and compact-renderer failure are confirmed on the reported phone. The host exposes local diagnostics at `window.cybrLight.snapshot().gpuSession`; it does not upload them.

The bounded NVIDIA / Lovelace check passed at the reported 960×540, six-bounce, one-optical-sample proof-optics configuration. After eight identical frames, raw transport, temporal reconstruction and final output hashes matched the preserved live version exactly. The mobile-layout session used serial compilation with GPU timing disabled. Intentional device loss exposed the reason and retry button; retry rebuilt a ready renderer with the same settings. Explicit persisted page lifecycle events closed the old device and restarted a fresh session. That lifecycle test does not prove Chrome elected to put the page in its back/forward cache, and none of these checks reproduce physical Adreno execution. Both actual canvas captures showed the glass/water scene; no static preview was substituted.
