# Mobile WebGPU recovery

## Physical-device retest: still unresolved

The user retested the live diagnostic build on physical Qualcomm / Adreno and still received `GPU device lost (unknown) during Compiling trace: A valid external Instance reference no longer exists.` The lifecycle/error-reporting improvements do not fix that startup failure. A passing desktop test cannot establish a phone fix.

The exact message can arise when Dawn cancels pending callbacks during API-channel teardown. [Dawn's wire client](https://raw.githubusercontent.com/google/dawn/main/src/dawn/wire/client/Client.cpp) destroys instance event managers on disconnect, and [Blink maps CallbackCancelled to JavaScript unknown](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/webgpu/gpu_device_lost_info.cc). This does not identify the Android browser/driver cause or establish JavaScript garbage collection as the cause. The displayed stage is the outstanding operation when failure became visible.

Source ordering shows no scene worker, scene GPU buffers, frame buffers or first frame submission before trace compilation. Only a 16-byte diagnostic uniform buffer and a configured canvas are present. Four shader modules are prepared before compute pipelines. The current trace is 24,033 UTF-8 bytes with 34 functions, a 64-entry private BVH stack, two 16-entry medium stacks, and nested guide/branch/bounce loops. Private WGSL data size is not measured GPU memory or register usage.

[GPU startup comparison](../browser/gpu-compile-check.html) runs one selected compile-only case and reports adapter/device/requested limits, module-validation completion, outstanding operation, allocation ordering, shader hash, and error/loss data. Controls include a tiny shader; an unused entrypoint in full trace source; current trace with renderer/default limits; workgroup-only and medium-capacity-only variants; both together; and the original startup prefix. One case runs per request and closes its device. A single 40-second deadline covers adapter/device requests, source preparation, shader-info requests and pipelines. A device delivered after timeout is destroyed. The prefix records each shader-info completion separately. The report can be copied; scene/frame buffers are not loaded by the check.

The first NVIDIA comparison advanced through the seven isolated compute controls, then stalled in the original-startup-prefix case. Its aggregate harness timed out before preserving individual reports; actual renderer comparisons did not start. That exposed the earlier diagnostic timeout's narrow coverage and prompted the whole-startup deadline above. The outstanding prefix operation and compatibility-output parity still require another coordinated GPU run. This is not evidence that the physical Adreno failure has the same cause.

The explicitly selected `gpuCompatibility=compact` candidate retains the actual renderer and all supported scene/settings/transport behavior. It uses 4×4 trace workgroups and ten medium slots, matching the existing maximum ten-bounce UI. Traversal capacity, Fresnel split, water/glass absorption/IOR, stochastic paths, terminal emission and reconstruction are retained. The normal/default path is unchanged. Corrected and separate-signal transport experiments require their original capacities and reject this candidate explicitly. This is a compiler-shape comparison pending physical-device validation, not a proven Adreno fix.

The reported device was Qualcomm / Adreno-8xx, on proof-optics, interactive temporal reconstruction, 960×540, six bounces and one optical lighting sample. Its visible error was `A valid external Instance reference no longer exists.` The adapter label is assigned after `requestDevice` succeeds. The original host caught pipeline, submission and timing-readback failures in the same status field; those could replace the device-loss reason.

The exact browser text is not sufficient to infer a JavaScript lifetime defect or a shader defect. A [WebGPU maintainer response](https://github.com/gpuweb/gpuweb/discussions/4676) identifies it as Chromium-specific and requests a detailed reproduction. The original host also had a separate confirmed lifecycle defect: `pagehide` destroyed its device and controls with no `pageshow` recovery for a cached document.

The host now owns the GPU, adapter, context and device through the session; records compilation/load/render phase; preserves loss reason and the first failure; cancels pending compilation when leaving or losing the device; and reloads a cached document into a fresh session. A visible retry button preserves selected settings and requests a fresh device. Mobile or explicit recovery sessions serialize pipeline compilation and omit optional timestamp queries/readback. Desktop defaults and explicit `gpuTimings=1` keep GPU timing. Buffer creation checks actual device allocation and storage-binding limits before asking the GPU for an invalid resource.

The lifecycle changes do not alter shader, geometry, resolution, sample/bounce, denoiser, reconstruction or transport math. The 64 recorded renderer implementation digests remain unchanged. The separately selected compatibility candidate changes only trace workgroup shape and medium capacity. Mobile compilation sequencing reduces concurrent driver compilation work, and removing optional queries avoids that diagnostic driver path; neither is presented as proof of the Adreno root cause.

CPU tests cover feature/limit negotiation, exact compilation descriptors/order, bounded compilation concurrency, loss/error precedence, cancelled startup, intentional shutdown and buffer limits. Browser validation must distinguish actual desktop GPU execution with mobile layout from physical Adreno execution. Physical-device success remains unverified until the reported session is tested again. The host exposes local diagnostics at `window.cybrLight.snapshot().gpuSession`; it does not upload them.

The bounded NVIDIA / Lovelace check passed at the reported 960×540, six-bounce, one-optical-sample proof-optics configuration. After eight identical frames, raw transport, temporal reconstruction and final output hashes matched the preserved live version exactly. The mobile-layout session used serial compilation with GPU timing disabled. Intentional device loss exposed the reason and retry button; retry rebuilt a ready renderer with the same settings. Explicit persisted page lifecycle events closed the old device and restarted a fresh session. That lifecycle test does not prove Chrome elected to put the page in its back/forward cache, and none of these checks reproduce physical Adreno execution. Both actual canvas captures showed the glass/water scene; no static preview was substituted.
